Development strategy · Dev_Harness

DevCouncil Execution Harness

A harness written only in Go and Rust that runs DevCouncil's tools natively rather than shelling out to them — ported function by function, governed by one flag registry, and built around an override seam that lets a human or an agent clear a block without anyone editing the gate.

Languages Go + Rust only DevCouncil tools native, not bridged Control one flag registry Blocks overridable, never invisible Status phases 0–3 landed

What the goal changed

An earlier draft of this plan kept Python for the planning council and reached DevCouncil through a subprocess bridge. Building in Go and Rust only, with the tools integrated natively, removes both of those — and that is a different architecture, not a stricter version of the same one.

Three consequences follow directly, and everything below is downstream of them.

There is no third plane. Python stops being a runtime and becomes two other things: the reference implementation each port is derived from, and the generator of the fixtures that prove the port correct. That is a real role and the work depends on it, but nothing in the harness executes it.

Native integration means owning the semantics, not the transport. Shelling out to dev verify is one line of Go. Reproducing what the verifier decides — the ladder order, the glob dialect, the tri-state resolutions, the four lease codes — is the actual work, and it is where a port silently diverges. So the port order is set by which semantics are hardest to get right and most expensive to get wrong, not by which commands are called most often.

A gate you cannot open is a gate people work around. Autonomous builders hit legitimate blocks constantly: a helper file the plan did not enumerate, a lockfile that genuinely must change. Without a sanctioned way through, the pressure goes somewhere worse — enforcement switched off wholesale, or the plan padded with speculative scope. The override seam exists so the answer to a block is a recorded exception rather than a disabled rule.

The invariant that survives every change above

A check that did not run must never look like a check that ran and passed. It is why an override produces an allow that still names the rule it cleared, why a disabled feature is reported on every run that used it, why a decision reached without the repo map records that fact, and why a malformed diff returns an error instead of an empty file list.

Two planes

The split is the same axis as before — CPU-bound determinism against IO-bound concurrency — but now it partitions everything rather than most things.

execution plane · Go

What runs

Agent loop, providers, fan-out, process supervision, task and lease state, the write gate, the flag registry, the override ledger, MCP transport. Waiting on tokens and coordinating concurrency.

analysis plane · Rust

What decides

Diff parsing, scope classification, coverage intersection, stub and effort heuristics, extraction, resolution, liveness. Deterministic, CPU-bound, byte-identical output required.

reference · Python

What proves it

Not a runtime. The incumbent each port is read from, and the authority that generates parity fixtures. It stays installed on the developer's machine and ships in nothing.

The two existing language decisions in these repositories were already consistent with this and neither document said so. rust-port/PLAN.md §5 argues Rust for the map engine — tree-sitter's canonical binding, rusqlite, rayon, and the cgo tax on every node visit. docs/01-language-decision.html argues Go for the harness — official SDKs, a supplied agent loop, goroutines for fan-out. Different workloads, same axis, no conflict.

What is built

Phases 0 through 3 have landed. Everything in this table compiles, is tested, and is gated by ./verify.sh: 40 Go tests and 32 Rust tests, held to 938 parity cases generated from the Python incumbent and three interop tests that drive both languages against one state.sqlite.

The device that keeps the two planes honest

Both languages implement the glob dialect, and a divergence between them would not crash — it would make the write gate and the orphan-diff check quietly disagree about which paths are in scope, in one language only. So neither implementation owns the contract: scripts/gen-fnmatch-parity.py generates testdata/fnmatch-parity.tsv from CPython, and both suites read that one file. 682 cases today. verify.sh also asserts the fixture's size, because a fixture that failed to load would let both suites pass while checking nothing.

Not yet ported — named rather than implied

  • The council, reporting, OKF, and the remaining tools. Roughly sixty of the seventy-six MCP tools have no port yet.
  • Everything above the gate — session log, turn driver, providers, fan-out, and the remaining DevCouncil tools.

How Rust came to own the store

Native task and lease state means reading DevCouncil's SQLite store, and Go has no SQLite in its standard library. Three options, genuinely different architectures — this is the one taken and what it costs.

OptionVerdictReasoning
Rust owns the store
rusqlite		 chosen No new Go dependency, and one SQLite build across both planes — pinned to 0.31, the same line rust-port already carries. Costs a boundary crossing on every lease check, which the harness does not have anywhere else yet.
Pure-Go driver
modernc.org/sqlite		 not taken Simplest code and no boundary, but a large new dependency on the execution plane and two SQLite implementations in one repository once devmap is linked.
cgo driver rejected earlier Forfeits static linking and simple cross-compilation — the properties Go was chosen for in the first place.
What the port had to get right, and nearly did not

Mutual exclusion lives in the database, not in the code. A partial unique index — ON task_leases (task_id) WHERE status = 'active' — is what makes two builders racing for one task resolve to a single winner. The active_for_task check before the insert only produces a friendlier error. A port that kept the check and dropped the index would pass every single-threaded test and hand two agents the same working tree. Twelve threads through twelve connections to one file now prove exactly one acquire succeeds.

The second trap is lazy expiry: reading a lease past its TTL marks it stale as a side effect, so expiry is observed on read and a reader must be prepared to write. And an unreadable timestamp is an error rather than a shrug — treating it as "not expired" would turn one corrupt row into a task nobody can ever take again.

The gate that actually mattered

Self-consistency proves nothing about a migration. During cutover dev tasks and the harness read the same file, so the real test drives both: Rust acquires and DevCouncil's own TaskLeaseRepository reads it back, then the reverse, then an expired lease that both sides must agree is dead. Breaking the timestamp format Rust writes fails two of the three — which is how a timestamp divergence would have surfaced instead of quietly letting the two disagree about when a lease died.

Those tests skip when DevCouncil is not importable, so verify.sh reports interop coverage separately rather than letting a green suite imply it ran.

Port order

"Important" means: on the critical path of every turn, deterministic enough to port faithfully, and expensive to get subtly wrong. Ranked, with the reason each earns its place.

The override seam

An override is not a way to make a block disappear. It is a way to make it accountable — which is a different mechanism, and a much safer one.

The policy ladder already sorts itself into two kinds of rule, and the port makes that structure explicit rather than inventing one. The rungs that fire before a task is consulted protect the repository, its credentials, and the agent client configs; no task scope authorises them and no grant clears them. The rungs that fire after are statements about this task's declared scope — and DevCouncil's own denial message for the commonest one already points at the remedy, "Expand scope with dev scope update".

Exactly one denial is agent-grantable, and it is the one the incumbent already tells the agent to resolve by widening scope. The others encode a decision someone else made deliberately — a file the planner marked read-only, a path the plan forbade, work attempted with no lease at all. An agent overruling those is an agent editing its own instructions.

What bounds a grant

  • Hard rules are refused twice, on independent paths: at issue time, and again when a grant is applied. The one boundary that must not leak gets two checks rather than one.
  • An agent grant is confined to its own lease's task and defaults to single-use. Reaching into another task's scope is refused even for a grantable rule.
  • Time-bounded by authority — 15 minutes for an agent, 8 hours for a human, both configurable and both ceilings rather than defaults.
  • A reason is required, because a grant nobody can review later is not worth recording.
  • The narrowest sufficient scope is the default. The harness builds the grant request from the decision itself — this rule, this path, this task — so widening it is a deliberate act.
The property that makes this safe rather than convenient

A granted decision reports allow, and never reports as a clean pass. It keeps the rule that fired, the grant ID, the grantor, and the justification. The run report separates writes that passed on the rules from writes that passed on a grant, so an evidence report can say "verified, with two scope exceptions granted by the operator" — which is a different and more useful claim than "verified".

The master registry

Every feature toggle and tunable in one typed, self-describing place — with three properties that separate a settings registry from a bag of booleans.

fails loud

Unknown keys are errors

A mistyped key in a config file or an unparseable environment value is reported, never ignored. MANVI_POLICY_FILE_MODE=advisery stops the process; it does not silently leave enforcement on and the operator believing otherwise.

explains itself

Values carry their origin

Override beats environment beats config beats default, and every lookup returns which layer won. "Why is enforcement off?" is answerable without guessing.

bounded by authority

Not everyone may turn everything off

Flags are startup-only, human-only, or agent-settable. Safety flags cannot be declared agent-settable at all — that is a compile-time-adjacent error caught when the catalogue is registered.

The registry's most useful output is Weakened(): every safety flag currently off its default, with the origin that moved it. It rides in the run report, so a green result produced under relaxed configuration cannot be summarised as a strict one. Turning a check off is allowed; making it look like the check passed is not.

# Gate strictness, mirroring DevCouncil's gates.mode vocabulary
policy.file.mode          enforce | advisory | off   safety, human-only
policy.command.mode       enforce | advisory | off   safety, human-only
policy.hard_rules.enabled true                       safety, startup-only

# The override seam
grants.agent.enabled      true                       safety, human-only
grants.agent.max_ttl      15m                        safety, human-only
grants.require_reason     true                       safety, human-only

# Migration switches — how a port is promoted, and rolled back
devcouncil.surface        native | bridge
codeintel.engine          rust | python | auto

# Providers
llm.provider.xai.enabled  false
llm.xai.base_url          ""                         deliberately unset

Advisory and off never demote a hard denial. An operator saying they do not want scope enforcement is not an operator asking to write to .env, and conflating those is how a mode switch becomes a security hole.

Providers, including Grok

Grok exists in DevCouncil today as a coding-CLI executor — grok -p, hooks, MCP config in .grok/config.toml. Wanting Grok models is a different capability, and it lands at a different seam.

SurfaceWhat it isStatus
Grok as an executor The harness launches Grok Build as a subprocess to implement a task, then verifies the result. Grok owns the loop. Exists in DevCouncil; ports as one of several executor adapters.
Grok as a provider xAI behind cx.llm alongside Claude and Gemini. The harness owns the loop and Grok is a model it routes roles to. New. Flags are defined; the adapter is Phase 5.

Both are worth having and they are not substitutes. The second is what makes Grok available for cheap fan-out or as a second opinion in the council, which is where a multi-provider harness earns its cost.

Deliberately unspecified here

llm.xai.base_url ships empty and no xAI model ID appears anywhere in the flag catalogue or this document. Endpoints, model identifiers, context limits, and whether the API is OpenAI-compatible must be read from xAI's current documentation at the time the adapter is written. A plausible default baked in now would be a guess wearing the costume of a fact, and would be discovered as a 404 rather than as a missing setting.

The structural bet is that the local OpenAI-compatible adapter and the xAI adapter share a transport and differ in base URL, auth, and capability descriptor — which is why both are flags rather than separate code paths. That bet is cheap to unwind if the documentation says otherwise.

Phases

Each ends in a command that can fail. The first two are done; ./verify.sh is that command today.

0Fixtures

Ground truth before code — landed

Generate parity fixtures from the Python incumbent for every semantic the port must reproduce. The glob dialect first, because it underlies every path rule in the subsystem.

Done when Both language implementations read one CPython-generated fixture, and the gate asserts the fixture's size so a failed load cannot pass as a clean run. 682 cases.

1Kernel + gate

Registry, write policy, overrides, flags — landed

The plugin kernel, the ported file-write ladder, the grant ledger, and the flag registry — with the consumer that composes them and a run report that keeps their interactions legible.

Done when Two fake plugins boot in dependency order regardless of config order and unwind in reverse; a secret path is refused to a human grantor; an agent clears its own unplanned-scope block once and is refused the second time; and advisory mode demotes a soft denial while leaving a hard one intact. 52 tests.

2State

Tasks and leases, natively — landed

The four lease codes and their recovery actions, lazy TTL expiry, renewal that refuses to resurrect a dead lease, and a force-steal reserved for human intervention — in Rust, on DevCouncil's own SQLite file.

Done when Twelve threads racing one task through twelve connections produce exactly one winner and eleven lease_held_by_other; and the Rust store and DevCouncil's own repository agree on ownership and expiry against the same state.sqlite. 15 tests, 3 of them driving both languages.

3Commands

Shell gate and git safety — landed

The allowlist, its uv run and cd unwrapping, redirect stripping, and the git-safety rules. Bypass flags, force pushes and protected-branch hard resets are hard severity: they protect the verification gates themselves, and a force push can erase the evidence the whole system reasons about.

One deliberate divergence, and it only tightens. The incumbent exposes the allowlist and git safety as two entry points, so a caller invoking only the first gets no git safety — and a task listing git * in its allowed commands would sail a force push straight through. The port folds safety into the front of the single entry point.

Done when A parity corpus produces identical decisions in Go and in the Python engine. 256 cases across normalisation, the allowlist with and without a lease, and git safety — every one generated by driving DevCouncil's own TaskPolicyEngine, and each verified to fail against a deliberately mutated port.

4Loop

Session log and turn driver

Append-only log with the model-visible-means-logged invariant asserted at runtime, the turn/step driver, and the four waterfalls. The gate mounts as a pre-execute listener rather than being called from the loop.

Done when A recorded session replays to a byte-identical message projection; a deliberately unlogged injection fails loudly; and denying at pre-execute short-circuits without the loop knowing why.

5Providers

Claude, Gemini, xAI, local

Adapters behind one streaming interface, with provenance carrying adapter-private replay state handed over only when one adapter owns both the historical and the target provider. Capability descriptors so an impossible request fails at assembly rather than as a 400.

Done when One session runs on every enabled provider by config change alone, and a cross-provider handoff drops reasoning state explicitly and logs that it did.

6Verify

The evidence gates, in Rust

Coverage intersection over the parsed diff, stub and effort heuristics, secret scanning, and the typed next-actions contract the repair loop routes on.

Done when A frozen corpus of recorded diffs produces the same verdicts and the same gap identifiers as the Python verifier, with every divergence enumerated and accepted individually.

7Fan-out

Sub-agents on the task DAG

Live agent handles, cancellation, and a spawn ceiling that lives in code rather than in a prompt. Leases are the mutual-exclusion primitive; the harness does not invent a second one.

Done when N searchers run concurrently and one failure does not take the batch down, and cancelling a parent releases every child lease within a bounded time rather than leaving tasks locked until TTL expiry.

Migration discipline

Five rules. Each was paid for by an incident already recorded in these repositories, which is why they are here rather than a generic checklist.

1. A fallback that absorbs every failure is indistinguishable from no migration

Seven DevCouncil consumers were documented as Rust-primary with a Python fallback. They were Python-only in practice: the client pointed at the Python schema, the Rust store failed closed on it, and every call took the fallback — on every invocation, since the pass landed. The code was correct; the behaviour was a no-op. Count the primary path and fail the build when the count is zero. The codeintel.engine and devcouncil.surface flags exist to make which path ran an explicit, reportable fact.

2. Availability requires evidence, not absence of error

An empty store answered "available" and returned zero results — and zero is a valid answer to almost every code-intelligence question, so nothing looked wrong. Availability now requires a committed generation and a non-zero node count. Every boundary the harness crosses gets the same test.

3. Unknown is not verified zero

A caller that cannot distinguish "no dead symbols" from "the analysis did not run" will eventually treat the second as proof of the first. Resolution state crosses the boundary intact rather than being flattened into an empty list — which is the same rule the Degraded field on every policy decision implements.

4. Divergence is enumerated and accepted, never zeroed

The Rust port's ledger records thirty-odd deliberate differences from the Python baseline, each with a justification and a test — including one where correctness of the graph's join key was chosen over bug-for-bug parity. A migration whose gate is "zero diffs" will either stall forever or quietly suppress the diffs. The gate is "every diff has a name and an owner."

5. Replace in the same change; never accumulate

A port that lands beside what it replaces doubles the surface permanently. Each phase above names what it retires. Where a rollback switch exists it is a flag with a reported value, not a second implementation kept warm indefinitely.

Where this goes wrong

Four failure modes, named up front so they are recognisable when they start.

The port diverges silently

This is the dominant risk and it has already been demonstrated once in miniature: Go's path.Match and Python's fnmatch disagree about a single character, and taking the obvious standard-library function would have narrowed every secret-path rule without any test failing. The countermeasure is that no port lands without a fixture generated from the incumbent. A port whose correctness rests on reading the original carefully is a port that is already wrong somewhere.

Overrides become the path of least resistance

If granting is easier than fixing scope, scope stops being maintained and the ledger fills with exceptions nobody reads. The counter-pressures are built in — single-use agent grants, short TTLs, required reasons, and a run report that separates granted passes from clean ones — but the real signal is the trend. A rising grant rate is a planning problem showing up in the gate, and should be read that way rather than tuned away.

The flag registry becomes a way to avoid decisions

Every hard question can be deferred by adding a flag, and a registry with a hundred entries is a configuration surface nobody understands and every deployment sets differently. A flag should exist because two deployments genuinely need different answers — not because the right default was hard to choose.

The rewrite outruns the thing it replaces

DevCouncil is 93,941 lines and under active development. A port that targets a moving incumbent while the incumbent keeps moving never converges. This is what the port order is for: each item is a bounded surface with a frozen fixture set, and finishing one before starting the next is what keeps the target still.
