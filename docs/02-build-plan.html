Seam Harness Build Plan

A lightweight multi-provider agent harness in Go and Rust, borrowing DeepSeek Harness's plugin model — a service registry, declared injection, typed events, and reversible effects — without borrowing its 453,000 lines.

Host Go Plugin SDK Rust → WASM Providers Claude · Gemini · local Pattern source deepseek-ai/deepseek-harness (MIT) Target ~8k LOC

What we take, and what we leave

dsh is roughly 453,000 lines of TypeScript across ~219 workspace packages, in developer preview with breaking changes expected. You asked for lightweight. So this is a port of the ideas, at about 2% of the scope.

Take: the Cordis plugin contract, the three-role seam definition, the durable session log with its one invariant, the turn/step event flow, and the provider-neutral content-block vocabulary. These are the load-bearing designs and they're all small.

Leave: the web UI, the 219-package split, profiles/bundles as a distribution format, the generated-SDK "code mode", E2B sandboxing, projections and projection caches, telemetry backends, skill providers, and the ACP surface. Every one of those is a real feature and none is on your critical path.

Read this before copying anything

dsh is four days old and its README says plainly there will be compatibility-breaking changes. Treat it as a design reference to read, not a dependency to track. Copy the shapes into your own types; don't try to stay compatible with a preview API.

The five ideas, ported

Cordis states its model in five points. Two of them rely on TypeScript features neither Go nor Rust has, so those need a different mechanism — and one of them lands better in Rust than in the original.

Cordis ideaGoRust
Plugin is a service with inject + apply(ctx) Plugin interface: Name(), Deps() []string, Apply(*Ctx) (Dispose, error) trait Plugin with DEPS: &[&str] and fn apply(&self, cx: &Ctx) -> Result<Guard>
Context is a repository of services keyed ctx.<key> map[string]any + package-level generic Resolve[T](cx, key) — Go can't put type params on methods HashMap<TypeId, Arc<dyn Any + Send + Sync>> — the classic type-map; TypeId beats string keys
Dependency via inject, load order from requirements Topological sort over Deps() at boot; cycle is a boot error, not a hang Same, with inventory for compile-time plugin registration
Typed events, four dispatch modes Generic bus: On[E](bus, fn) / Emit[E] / Waterfall[E]. No declaration merging — events are concrete types in one package Same shape; tower::Layer + Service is already exactly the waterfall pattern
Registrations are reversible effects Return a Dispose func() error; host unwinds LIFO. Discipline, same as TS Better — Drop makes teardown a type-system guarantee, not a convention

Cordis says "every registration should have a disposer" as a rule authors must follow. In Rust that rule is enforced by the compiler: a registration returns a guard, and dropping the guard unwinds it. This is the one place the port improves on the original, and it's a decent argument for putting policy plugins on the Rust side eventually.

The seam definition — keep this strictly

dsh defines a seam as three roles: a Service Definition declaring the interface, a Service Provider implementing it, and a Consumer using it. A package holding one role alone is not a seam. Adopt this literally — it's what stops "plugin architecture" from decaying into a folder of loosely related files. In Go, that means the interface lives in its own package that neither implementation nor consumer owns.

The plugin mechanism problem

"Everything is a plugin, replaceable from configuration" is easy on Node. Neither Go nor Rust can load code dynamically in-process without serious caveats, so this needs three tiers instead of one.

Why not dynamic loading

Go's plugin package requires the identical toolchain and identical dependency versions between host and plugin, has no unload, and is effectively Linux-only in practice. Rust has no stable ABI, so dylib plugins break across compiler versions. Neither is a foundation to build on — plan around this rather than discovering it in month two.

Tier 1 carries the weight. "Replaceable from configuration" does not require dynamic loading — it requires that every service is resolved by key and selected by config. A compiled-in registry where llm.provider: gemini swaps the adapter gives you the whole benefit with none of the ABI pain.

Verified constraint · Tier 2

wazero supports WASI Preview 1 and has Preview 2 component-model integration only in an experimental package. Do not build the plugin ABI on the component model yet. Use core WASM plus WASI p1 with a hand-rolled JSON-over-linear-memory calling convention: two exported functions (alloc, invoke) and a length-prefixed buffer. It's unglamorous, it's stable today, and it's about 150 lines on each side. Revisit components when wazero's support leaves experimental.

The seams to build

Seven. dsh has roughly forty; these are the ones without which nothing runs.

cx.llm

Provider registry

Named adapters behind one streaming interface. Claude, Gemini, local OpenAI-compatible. The heart of this plan.

cx.sessions

Session log

Append-only event log. The source of truth for what the model saw. Everything else projects from it.

cx.tools

Tool registry

Schemas plus a guarded execution pipeline with pre/execute/post waterfalls — where approval and policy attach.

cx.systemPrompt

Prompt assembly

Sections registered by plugins, composed per step. Stops the system prompt becoming one hardcoded string.

cx.agentLoop

Loop driver

The default turn/step driver. Pluggable so a planner loop and a builder loop can differ without forking the host.

cx.agents

Agent registry

Live agent handles, inbox, status, cancellation. Where fan-out and sub-agent spawn live.

cx.credentials

Credentials

Keys resolved per provider, never in config files. Thin, but a seam from day one — retrofitting it is painful.

cx.subprocess

Subprocess — later

Shell execution behind an interface so local, container, and WASM backends swap. Add at Phase 5.

Multi-provider: the part that's actually hard

Fanning out to Claude and Gemini is not "write two HTTP clients." The difficulty is that provider-private state has to survive a round trip through a provider-neutral log.

Start from dsh's content-block vocabulary, which is already provider-neutral and well chosen:

// Provider-neutral. Every adapter maps to and from these.
type ContentBlock interface{ blockType() string }

TextBlock       { Text string }
ReasoningBlock  { ... }  // thinking, distinct from visible text
ImageBlock      { ... }
ToolCallBlock   { ID CallID; Name string; Arguments json.RawMessage }
ToolResultBlock { ToolCallID CallID; Content []ContentBlock; IsError bool }

Now the trap. Anthropic requires thinking blocks be echoed back unchanged on the same model, and other models drop them. Gemini has its own equivalents. A naive neutral log destroys this state and you get subtle, hard-to-trace quality loss — or 400s.

dsh solves it with provenance carrying adapter-private replay data, exposed only when the adapter owns both the historical and the target provider:

type AssistantProvenance struct {
    Provider string
    Model    string
    // Lossless adapter state needed to replay the provider response.
    // Handed to an adapter ONLY when it owns both the historical
    // provider and the target provider. Otherwise: dropped.
    ReplayState json.RawMessage
}
Steal this one

Of everything in dsh, replayState gated on adapter ownership is the highest-value idea for a multi-provider harness, and it's maybe 40 lines. It lets the log stay neutral while each provider keeps its lossless state, and it makes cross-provider handoff explicitly lossy rather than accidentally lossy.

Each adapter also declares a capability descriptor — context window, whether it supports reasoning, tool-calling shape, effort levels — so the loop can refuse an impossible request at assembly time instead of discovering it in a 400.

Turn flow and the event set

Port dsh's flow directly. It's the most carefully designed part and there's no reason to invent a different one.

turn/start
  claim next-step input + one queued message
  assemble prompt sections + tool schemas
  -> agent/pre-step        waterfall   reject | rewrite messages
     step/start
     agent/request         waterfall
     llm/stream            waterfall   -> assistant/chunk* -> assistant/message
     tool/call*
       tools/pre-execute   waterfall   approval, policy, budget
       tools/execute       waterfall
       tools/post-execute  waterfall   redaction, truncation
     tool/result*
     step/end
  -> agent/turn-stopping   serial
turn/end

The four waterfalls are the whole extension story. A waterfall listener receives (args, next): call next() to delegate, return without it to short-circuit and own the decision. That's around-middleware, and it maps cleanly onto Go's standard middleware idiom and onto tower::Layer in Rust.

Concretely, your approval gate is a tools/pre-execute listener that short-circuits; your DevCouncil policy check is another one beside it; neither needs to know the loop exists.

Port this invariant verbatim

Model-visible means logged. Anything that reaches a model request must be reconstructable from the session log, asserted at runtime. This is the difference between a harness you can audit and one you can only watch. It also lands exactly on your DevCouncil provenance story — a task's evidence chain becomes a projection of the log rather than a second thing to maintain.

Phases

Each is useful standing alone, and each has a check you can actually run. Stop whenever the harness is doing what you need.

1Core

Registry, events, effects

The Cordis kernel in Go and nothing else: service registry with generic Resolve, topo-sorted boot over declared deps, the typed event bus with four dispatch modes, LIFO teardown. No LLM, no tools.

Done when Two fake plugins, one depending on the other, boot in dependency order regardless of config order, and unloading the dependency unwinds both registrations in reverse.

2Log

Session log + replay adapter

Append-only event log, deriveMessages() projection, and the replay provider reading recorded fixtures. Build the fake provider before the real ones so every later phase is testable offline and for free.

Done when A recorded session replays to a byte-identical message projection, and the model-visible-means-logged invariant fails loudly on a deliberately unlogged injection.

3Loop

Turn/step driver + tool pipeline

The flow above, with all four waterfalls wired. Two tools only: read and bash. An approval listener on tools/pre-execute proves the seam.

Done when A replayed session drives a full multi-step turn with tool calls, and denying at tools/pre-execute short-circuits without the loop knowing why.

4Providers

Claude, Gemini, local

Three real adapters behind cx.llm, plus provenance and ReplayState. Capability descriptors so impossible requests fail at assembly.

Done when The same session runs on all three by config change alone, and a Claude-then-Gemini handoff drops reasoning state explicitly and logs that it did — rather than silently corrupting history.

5Fan-out

Sub-agents and orchestration

cx.agents with live handles, inbox, cancellation. Fan-out via errgroup, results merged in plain Go — not by another model call. Deterministic spawn cap in code, not in a prompt.

Done when N searchers on cheap models run concurrently, one failure doesn't take the batch down, and cancelling the parent cancels every child within a bounded time.

6Rust

WASM plugin SDK

wazero host, the two-function ABI, and a Rust guest crate that makes writing a tool a matter of implementing one trait. Port one real tool across as proof.

Done when A Rust tool compiled to WASM runs with no filesystem or network capability granted, and attempting either fails cleanly rather than escaping.

7Wire

DevCouncil and Dev Map

Tier-3 MCP or subprocess plugins exposing map_query, map_trace, map_dead, graph_ctx, and the task lifecycle. State stays in DevCouncil; the harness never keeps a second copy.

Done when dev map dead exiting 3 on a stale index surfaces to the agent as a tool error, not as an empty result.

Where this goes wrong

The three failure modes worth naming up front.

Building the plugin system before you have two plugins

Abstraction with one implementation is guesswork. Phase 1 mandates two fake plugins for exactly this reason, and the provider seam only earns its shape once Claude and Gemini are both behind it. If you find yourself designing tier-2 WASM ABI details in week one, that's the smell.

Porting dsh's package granularity

219 packages is right for a project with many contributors and a public plugin ecosystem. At your scale it's overhead that buys nothing. Seven seams, roughly a dozen packages. The seam rule — definition, provider, consumer split — is what you're preserving; the count is not.

Letting the harness own state DevCouncil already owns

Tasks, goals, gaps, verification evidence, and write policy already exist in this repo with a lease model and a policy gate. The harness should read and write them through the boundary, never mirror them. Two task tables that drift is a worse failure than no harness at all.

Open question

This plan puts the host in Go and Rust in tier 2 only, which is the split that has a clear technical reason behind it. If you want Rust higher up — the whole kernel, with Go only for provider SDKs — that's defensible too, but it costs you the official Anthropic SDK and the supplied agent loop, and the seam then runs across a process boundary instead of a sandbox boundary. Worth settling before Phase 1, because it changes Phase 1.
