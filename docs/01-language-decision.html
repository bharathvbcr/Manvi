Rust or Go for the Harness

Building a self-hosted multi-agent coding harness — planner, search fan-out, orchestrator, builders. Which language actually gets you there faster, what open source already exists, and what you should not rebuild.

Verdict

Go, by a wide margin — mostly because of what already exists, not because of the language.

Anthropic ships an official Go SDK with a built-in agentic tool-runner loop. There is no official Rust SDK. That single fact means the Go harness starts at "wire up tools and orchestration" while the Rust harness starts at "write an SSE parser and a tool-schema deriver." Add Google's ADK-Go 2.0 (graph workflow engine, sub-agents, A2A) and ByteDance's Eino, and Go has two mature multi-agent frameworks that map onto your topology almost directly.

Where Rust genuinely wins

One place, and it's real: sandboxed tool execution. AutoAgents runs tools in a WASM sandbox — if you want builder agents executing generated code without trusting it, that's a capability Go has no equivalent for. Also worth weighing if you intend to embed the harness into Rust_MLKit/ rather than run it as a separate process.

The performance argument for Rust does not apply here. A coding harness is IO-bound on model tokens — a builder agent spends 99% of wall time waiting for the API. The 5× memory and 25–44% latency figures cited for Rust agent frameworks are measuring the wrong axis for this workload.

Your design names "3.7 Flash" as the cheap fan-out worker. That isn't an Anthropic model — Flash is Google's naming. Here is the actual roster to assign roles from.

Cost shape

Search fan-out is where the money goes — many agents reading many files. Haiku at $1/MTok input versus Opus at $5 makes a 5× difference on exactly the workload you fan out the most. Keep the 200K context in mind: a Haiku searcher can't hold what an Opus orchestrator can, so give each one a narrow, self-contained question.

If Gemini Flash is deliberate, not a slip

Flash is Google's line, and using it for cheap fan-out alongside Claude for building is a reasonable cost architecture. But it makes the harness multi-provider, and that shifts the framework decision:

  • The Anthropic Go SDK is Anthropic-only. Multi-provider means you write a provider abstraction, or adopt a framework that already has one.
  • ADK-Go gets substantially stronger — it's Google's own kit, so Gemini support is first-class, and it's explicitly model-agnostic for Claude.
  • Eino already integrates OpenAI, Claude, Gemini, and Ollama behind one ChatModel interface.
  • On the Rust side this is the one thing rig is genuinely best at — 20+ providers behind a single interface is its core value proposition.

Verify current Gemini model IDs, pricing, and context limits against Google's own documentation before wiring anything — I'm not asserting them here.

The open-source field

Everything below is Apache-2.0 or MIT. Star counts are as reported by GitHub at the time of writing.

Go

Google ADK-Go

~8.7k ★ · Apache-2.0. The closest fit to your design. Version 2.0 added a graph-based workflow engine as a first-class way to compose multi-agent applications, plus built-in human-in-the-loop and dynamic orchestration. Supports the A2A protocol for agent-to-agent collaboration, MCP tools, and modular sub-agent composition.

If you want the orchestrator → planner → builder topology handed to you rather than assembled, start here.

Go

CloudWeGo Eino

~12.7k ★ · Apache-2.0 · ByteDance. The most-starred Go AI framework. Composable components (ChatModel, Tool, Retriever, ChatTemplate) wired into graphs and workflows, with its own ADK layer on top: DeepAgent multi-agent coordination, ReAct loops, human-in-the-loop interrupt/resume, and state checkpointing.

Checkpointing is the differentiator for long orchestrator runs — an overnight build that dies at hour three resumes instead of restarting.

Rust

rig

~8.3k ★ · MIT. The de-facto Rust LLM library. 20+ providers behind one interface, 10+ vector stores, streaming, OpenTelemetry. Split into rig-core (provider-agnostic contracts) and rig-agent (builder runtime).

Single-agent by design. No built-in orchestrator — multi-agent patterns are composed manually. You'd be building your topology on top, not with it.

Rust

AutoAgents

~734 ★ · MIT/Apache-2.0 · Ractor actor model. The only Rust option with real multi-agent primitives: typed pub/sub messaging, environment lifecycle management, ReAct executor, sliding-window memory, MCP examples, OpenTelemetry.

The standout feature is a sandboxed WASM runtime for tool execution. Much smaller community than the Go options — weigh that against the sandboxing.

Rust

ADK-Rust · Swiftide

ADK-Rust (zavora-ai, community — not Google) mirrors the ADK shape in Rust with models, tools, memory, MCP/A2A/ACP, and realtime voice. Swiftide offers an agent harness plus typed task graphs and streaming RAG pipelines.

Both are plausible; neither has the adoption of rig or the Go pair. Verify current maintenance before committing.

Go · Reference

Anthropic Go SDK direct

Apache-2.0 · first-party. The zero-framework option. toolrunner.NewBetaToolFromJSONSchema defines tools, client.Beta.Messages.NewToolRunner(...) drives the loop, .RunToCompletion(ctx) runs it out. You write the orchestration; the SDK writes the loop.

For a harness you want to stay lightweight, this plus errgroup may beat either framework.

Your topology, and the one constraint that bites

Planner fans out searchers, orchestrator breaks down tasks, builders spawn sub-builders and report back. Here is what that looks like with models assigned.

The constraint

Anthropic's Managed Agents supports one level of delegation only: a roster member must not itself carry a multiagent roster, and that's enforced at agent-save time, not silently flattened. Your builders-spawn-sub-builders design is depth 2. If you want it, you self-host the harness — which is what you were asking about anyway. Just know that "use Managed Agents instead" is not a shortcut that gets you this topology.

The other reason to self-host: dev map and your repo live on your machine. Managed Agents runs tools in an Anthropic-hosted container by default. You'd need a self-hosted sandbox environment plus a polling worker — and the worker helpers exist in Python, TypeScript, and Go only. Another Go point; Rust has no path here at all.

Don't rebuild tasks, goals, or gap detection

This repo already has the task layer. Building a second one inside the harness gives you two sources of truth that drift.

Wiring Dev Map in as tools

Subprocess-shelling a CLI is trivial in either language. What matters is the tool descriptions and one failure mode.

Four tools cover the search agents' needs. Every one of these already emits JSON with --json:

// Prescriptive descriptions — say WHEN to call, not just what it does.
// Current models under-reach for tools described only by function.

map_query   → dev map query <symbol|path> --json
              "Call this first when you need a symbol's definition, callers,
               callees, and importers. Faster and more complete than grep."

map_trace   → dev map trace <a> <b> --json
              "Call this when you need to know whether and how one symbol
               reaches another — before claiming code is connected."

map_dead    → dev map dead --json --confidence extracted
              "Call this before deleting anything. 'extracted' is verified;
               'inferred' is a guess and must not be treated as proof."

graph_ctx   → dev graph-context <files...>
              "Call this when reviewing a change set, to pull the
               code-review-graph context for the touched files."
Fail loud, not quiet

dev map dead exits 3 when the index was built from a different commit than HEAD — deliberately, so stale results can't pass as evidence. Your harness must surface that exit code as a tool error with is_error: true, not swallow it and return an empty list. A check that could not run must never look like a check that ran and passed. Same rule for graph_degraded and empty entry_roots in the repo map: report the degradation to the agent rather than letting it reason over a silently broken graph.

Give the search agents map_query, map_trace, grep, glob, and read — read-only, nothing that mutates. Builders get those plus dev write / dev apply-patch, so every mutation passes through the existing policy gate rather than a raw file write.

Blending Rust and Go

It works, and there's exactly one seam worth using. But it closes capability gaps, not community gaps — those it makes worse.

The two languages' gaps here are complementary and non-overlapping, which is what makes a clean split possible at all:

Rust can't

Talk to model APIs

No official SDK, no supplied agentic loop, no self-hosted worker.

Go can't

Sandbox untrusted code

No WASM tool runtime; isolation is yours to build with containers or subprocesses.

Neither side needs the other's missing capability, so the boundary never has to be crossed twice. Go owns everything that talks to a model; Rust owns anything that executes code you don't trust.

Use WASM as the seam. Do not use cgo.

cgo is the tempting answer and the wrong one. It costs you the properties that made Go attractive in the first place:

  • Cross-compilation stops being GOOS=linux GOARCH=arm64 go build — you need a C toolchain for every target, or Zig as a stand-in.
  • CGO_ENABLED=1 gives up the drop-anywhere static binary. Distroless and scratch images mean pinning glibc or moving to musl and accepting the behavioral differences.
  • Every foreign call routes through runtime.cgocall, transitioning the goroutine through entersyscall/exitsyscall.

wazero avoids all of it: a pure-Go, zero-dependency WebAssembly runtime, so CGO_ENABLED=0 and simple cross-compilation both survive. It has been 1.0 since March 2023 and is the default WASM runtime across the Go ecosystem — Trivy, Cilium, Tetragon, dapr, k6, and Open Policy Agent all embed it.

So the architecture isn't really "two languages running side by side." It's Go as the host, Rust as a compile target:

Go binary (single static artifact, CGO_ENABLED=0)
├── Anthropic / Gemini clients ....... official SDKs
├── orchestrator + fan-out ........... goroutines, errgroup
├── DevCouncil state ................. subprocess → dev CLI
└── wazero runtime
    └── tool.wasm .................... compiled from Rust
        capability-sandboxed: no syscalls unless granted

You get Rust's sandboxing inside one Go binary — no second process, no cgo, no lost static build.

The part that doesn't work

A blend does not merge communities — it doubles them. You'd carry the Go module ecosystem and the Rust crate ecosystem, two CI toolchains, two dependency-audit surfaces, and a WASM ABI contract to version between them. The capability gaps you close are one-time wins; the ecosystem cost is paid every week, and for a solo developer it usually dominates. "Blend to get both communities' tools" is the one goal this architecture cannot deliver.

You already have three seams doing most of this work

Before adding a language, check which gap isn't already covered by a boundary in this repo:

Your local-model story in particular needs no Rust seam: scripts/serve_qwen.py already exposes an OpenAI-compatible endpoint, so the Go harness routes fan-out to a local model over plain HTTP for zero marginal cost per token.

Recommendation: build Go-only, and keep wazero as a documented escape hatch. Add Rust when you have a specific tool that must execute untrusted generated code, or when you want Rust_MLKit in-process rather than behind HTTP. Adding it before then buys complexity against a gap you haven't hit.

What I'd actually build

Ordered so each step is useful on its own and you can stop at any point.

  1. Single-agent Go loop against the SDK tool runner

    One agent, the four Dev Map tools, no orchestration. Proves the tool layer and the exit-code handling. A few hundred lines.

  2. Search fan-out with errgroup

    N Haiku agents on independent questions, results collected and deduped in plain Go — not by another model call. This is the step where Go's concurrency story pays for itself.

  3. Orchestrator backed by DevCouncil

    Opus reads the search digest, calls dev plan / next-task, and hands scoped tasks to builders. State lives in DevCouncil's SQLite, not in the harness.

  4. Builders with depth-2 spawn

    Cap the spawn count deterministically. Opus 5 delegates readily — an explicit ceiling in code beats a prompt instruction.

  5. Only now consider a framework — or a second language

    If checkpointing and resume become the bottleneck, port to Eino. If the graph topology gets unwieldy, or you commit to multi-provider with Gemini, port to ADK-Go 2.0. If builders start executing generated code, add wazero and a Rust tool module. You'll know which by then — and you'll have a working harness either way.

Skipping straight to a framework is the main way this goes wrong. Both Eino and ADK-Go are large surfaces, and "lightweight, fast harness" is the thing you asked for. The Anthropic Go SDK plus errgroup plus DevCouncil is already most of the design.
